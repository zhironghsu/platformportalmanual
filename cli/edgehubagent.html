Advantech EdgeHub Agent Service (CLI)

Available Commands:

  -h, --help                          help for edgehub-agent
      --version                       version for edgehub-agent

Use "edgehub-agent [command] --help" for more information about a command.

On Windows, edgehub-agent.exe runs with the rights of the user who starts it. Running the agent itself, the service commands, the app commands, and the conn commands that change the connection (conn with a setting, enable, disable, reset and rollback-key) need a command prompt opened with Run as administrator, as changing the settings through the portal needs an account in the Administrators group; they say so when they lack it. conn status, conn mac and the wsl commands run in an ordinary command prompt. While the agent is not running, conn mac needs an elevated prompt, and only an elevated conn status also tells whether a connection setting is stored, as only administrators may read the agent's settings.

On Linux, run edgehub-agent as root, for example with sudo: the agent's socket admits only root, and only root may read its data directory. As any other user, running the agent and the service, app and conn commands stop and say that they need root.

Data Directories tells where the agent keeps its data, who may use it, and how to restrict a directory given with --config, which the agent refuses to start on otherwise.

Plain HTTP is off by default. To turn it on, give --insecure-port, or server.http.port in the config file, a port other than 8789: that was its default, and it now turns plain HTTP off. The exception is a device with HTTPS off (server.https.port 0), where that port stays on, because a service must keep one of the two.

  • conn command

    The device credential is set in the Dashboard or with POST /edgehub/api/conncfg; the conn command manages the stored one.

    conn mac prints the MAC the device holds, the one GET /edgehub/api/macaddr returns; POST /edgehub/api/conncfg says when a connected device takes a new one. conn mac --all also lists the network adapters whose MAC a device credential may name, as that section describes: the wired ones first, then the wireless ones, each in ascending order, with (current) after the MAC the device holds, which is listed as other when it is none of them. On Windows an adapter whose MAC is overridden is listed by its burned-in MAC as well.

  • app command

    The agent hands an application credential only to the operating system account that owns the application's registration in the cloud. That is the account whose request made the cloud register the application, or, for a registration the cloud already had and no account on the device owned, the first account that asked for it: one registered in EdgeHub, one deleted in EdgeHub and registered again under the same name, which gets a new registration, or one whose first request got no answer. A request from any other account is refused with 403 Forbidden. On Windows the account is the Windows user the application runs as, SYSTEM included; on Linux it is the user ID, root included. A container counts as the account that runs its container engine: root for a rootful engine, the user for a rootless one, and in WSL 2 the Windows user who ran wsl setup for the distribution; the user ID inside the container does not count. On Linux an account whose user ID is from 61184 to 65519, the range systemd gives services with DynamicUser=yes their user IDs from, owns no application, and its requests are refused: systemd gives these user IDs to such services one after another, so whichever service held one next would receive the applications of the one before. Run such a service as a User= whose user ID is outside that range, DynamicUser=yes may stay, and a rootless container engine as a user outside it too. Before deleting a user, release its applications: its user ID may be given to the next user created. Administrators are bound like any other account.

    The agent keeps these records for its own device registration. Connected to the cloud of another site, it starts there with none, and finds its records again when it connects back. A record names the registration it is about, so when the cloud registers a name again, the record of the earlier registration stays beside the new one's. Each record also keeps its site, the MQTT broker host the device credential named when the record was made: two clouds can give a device the same devId, and the app commands by name act only on the records of the site the agent is connected to. The owner of a registration is decided by its uuid alone, so the owners keep their registrations when a cloud moves its broker.

    The app commands need an elevated command prompt, or root on Linux, and a running agent:

    edgehub-agent app owners
edgehub-agent app assign --type SCADA --name plant-a --account "DOMAIN\user"
edgehub-agent app release --type SCADA --name plant-a
edgehub-agent app release --uuid 00000000-0000-0000-0000-000000000000

    owners lists the applications that have an owner, one line for each registration, with its site. assign makes an account the owner of an application in place of the account that owned it, also before the application is registered: whichever registration the cloud holds under the name when the next request at this site reaches it goes to that account. A later assignment of the name replaces an earlier one. The account is a user name or a SID on Windows, and a user name or user ID on Linux; app assign --help says where to find the account a program runs as. A group cannot own an application: a program runs as one account, never as a group. On Linux neither can a user ID from 61184 to 65519, the range systemd gives services with DynamicUser=yes their user IDs from. On Windows the account has to be one the system can look up: a user, SYSTEM, LOCAL SERVICE, NETWORK SERVICE, or a virtual account such as NT SERVICE\name. Give a user of the device as COMPUTERNAME\user: a name without a domain also finds a domain account when the device has no user of that name. A service's account can be given as sc.exe qc prints it, LocalSystem and .\user included. A domain account cannot be assigned while no domain controller answers. release removes the records of an application at this site, of each of its registrations, and each registration goes to the next account that asks for it. Both take the name in any letter case. release --uuid removes the record of one registration made at any site, such as one of another cloud or one the cloud has deleted.

    An application registration belongs to the operating system account whose
process made the cloud create it, or, for one the cloud already had that no
account here owned, to the first account that asked for it; the agent hands
its credential to that account only. A container acts as the account that
runs its engine. A registration the cloud creates anew under a known name,
with a new uuid, is nobody's until an account asks for it; the record of the
earlier one stays. Records are kept per device registration of the agent, so
they follow the cloud the agent is connected to, and each keeps its site, the
broker the device credential named; by name, these commands reach the records
of the site the agent is connected to. They need administrator rights and a
running agent.

  • wsl command (Windows only)

    Containers in WSL 2 on a Windows device, run by Docker or Podman in a WSL distribution or in a Podman machine, reach the agent through a relay in that distribution. edgehub-agent.exe wsl setup installs the relay as a systemd service that starts with the distribution. Run it once for each distribution a container engine runs in, and again after upgrading the agent, to update the relay. Docker Desktop is not supported.

    Every wsl command takes the distribution's name, as wsl --list shows it, in --distro:

    edgehub-agent.exe wsl setup --distro Ubuntu-22.04

    For a Podman machine, pass the machine's name or its distribution name, for example --distro podman-machine-default.

    Before running setup:

    • The distribution runs systemd, as Ubuntu installed with wsl --install does by default. Otherwise add systemd=true under [boot] in the distribution's /etc/wsl.conf, run wsl --terminate <name>, and start the distribution again. A Podman machine runs systemd.
    • The container engine serves its API socket in the distribution. Docker does while it runs; rootful Podman does once podman.socket is enabled, with sudo systemctl enable --now podman.socket. A Podman machine does.
    • The agent service is running.
    • The command runs as the Windows user the distribution belongs to, in an ordinary command prompt. An elevated prompt that runs as another administrator account sees that account's distributions instead. The agent service cannot install the relay itself, because a WSL distribution belongs to a user.

    setup asks the agent for a relay key of the Windows user who runs it, which the agent issues on the first request and keeps where only administrators and SYSTEM can read it, and installs it in the distribution. Every caller the relay passes on counts as that Windows user, as all the WSL distributions of a Windows user run in one virtual machine of that user. setup checks the distribution before it replaces anything, and changes nothing if a check fails. At the end it runs a short-lived container to confirm that the relay identifies containers; if that fails, the new relay stays installed and setup says what failed. status shows the relay in the distribution and what the agent sees of relays, which GET /edgehub/api/wsl/status also reports; remove stops the relay and removes what setup installed.

    A container that provisions an application credential through the agent needs the distribution's /run/edgehub directory mounted, read-only is enough, and two labels set when the container is created. Applications that follow the EdgeHub Connect SDK documentation read the same type and name from two environment variables, which the example sets too:

    docker run -v /run/edgehub:/run/edgehub:ro \
  --label com.advantech.edgehub.app.type=Application \
  --label com.advantech.edgehub.app.name=line-3-sensor \
  -e EDGEHUB_APP_TYPE=Application \
  -e EDGEHUB_APP_NAME=line-3-sensor \
  <image>

    com.advantech.edgehub.app.type is Application, EdgeLink or SCADA, and com.advantech.edgehub.app.name is the name of the application the container provisions. The agent allows the container exactly that type and name, in the same letter case, and only an application the Windows user who set up the relay may have, as the app command above describes: a request for any other, or from a container without the labels, is refused with 403 Forbidden. Only the labels carry authority; the environment variables only tell the application what to ask for. If the container engine does not answer when the relay looks up the labels, or the relay cannot reach the agent, the request is refused with 503 Service Unavailable and can be retried. The same options work with podman run, also from Windows against a Podman machine.

LAN onboarding

LAN onboarding lets a utility on the local network, such as the EdgeHub utility, find this device over mDNS and register it with EdgeHub without logging in to the device. It is off by default: the agent does not advertise itself, has no initial code, and answers 404 Not Found on POST /edgehub/api/initialcode, POST /edgehub/api/device/challenge and POST /edgehub/api/device/register. Its HTTPS port listens on this host only, unless server.https.address names another address, and other hosts reach the agent through the portal.

To turn it on, stop the service, add this to config.yaml in the agent's data directory, and start the service again. A running agent rewrites that file and reads the setting only as it starts, so change the file while the service is stopped:

device:
  lanOnboarding: true

The initial code is broadcast in plain text. While LAN onboarding is on, anyone who can hear mDNS can register a device that has no stored connection configuration, so turn it on only on a trusted network, and only while it is needed. Set the value back to false, or remove it, to turn LAN onboarding off.

While LAN onboarding is on, the agent's HTTPS port listens on all interfaces when server.https.address is blank, for the utility to reach it. A client on another host reaches only the device challenge and registration there, and gets 403 Forbidden for any other request, on any address the agent listens on; programs on this host and requests through the portal are served as before. Plain HTTP stays on this host only when server.http.address is blank.

When an application is refused

An application the agent refuses its credential gets 403 Forbidden; an application built on the EdgeHub Connect SDK reports EHC_PROVISION_ERROR_NOT_AUTHORIZED, and its error text holds the agent's reason, which the agent also writes to its log. Asking again gets the same answer until the cause is removed; then restart the application, or let it ask again. A caller the agent failed to identify, the second group under the caller could not be identified below, gets 503 Service Unavailable instead, which the SDK reports as EHC_PROVISION_ERROR_AGENT_UNAVAILABLE, with the reason too. By the reason, where ... stands for the part that differs from case to case:

  • ... "...": the application belongs to another account on this device

    First check that the type and name the message starts with are the application's own: a program that asks for another application's name gets this answer too, and has to ask for its own name instead. If they are its own, the application runs as another operating system account than the one that owns its registration: for example, it was first started as another user, or another program asked for the same name first. An administrator sees the owner with edgehub-agent app owners. Run the application as that account or, once sure the application is the one meant to have the registration, have an administrator assign it to the account the application runs as with edgehub-agent app assign; edgehub-agent app assign --help says how to find that account. An assignment takes the application from its current owner.

  • this container is deployed as ... and may provision only that application

    The application in the container asks for another application than the one the container's labels name, which the message gives. If the labels are right, have the application ask for the type and name the message gives. If the labels are wrong, create the container again with the labels com.advantech.edgehub.app.type and com.advantech.edgehub.app.name set to the application's type and name, in the same letter case.

  • this container was deployed without an application identity

    The container has no labels naming its application. Create the container again with the labels com.advantech.edgehub.app.type and com.advantech.edgehub.app.name set to the application's type and name, in the same letter case.

  • this endpoint serves host processes; a container provisions through /run/edgehub/app.sock

    A container reached the agent's own socket, which serves programs on the host only. Mount /run/edgehub into the container instead, read-only is enough, and ask through /run/edgehub/app.sock.

  • uid ...: this account can own no application: systemd gives the uids 61184 to 65519 to services with DynamicUser=yes, one after another; ... (Linux)

    The application runs as a user ID that systemd gives to services with DynamicUser=yes, and may give to another service later; for an application in a container, the user ID is that of the user who runs the container engine. Run the application, or the engine of its container, as a user whose user ID is outside that range. For a systemd system service, an administrator adds User= naming such a user to the service's unit, DynamicUser=yes may stay, then runs systemctl daemon-reload and restarts the service. Should the application already belong to another account, the next request is refused for that reason, as the first entry describes.

  • the caller could not be identified: ..., or the account of the caller could not be read: ...

    The agent could not tell which account is asking; the rest of the message says why. These reasons are what the agent found out about the caller, and get 403 Forbidden:

    • the caller opened the pipe anonymously; ... (Windows): the program opened the agent's pipe without letting the agent read its account. Open the pipe at the SECURITY_IDENTIFICATION impersonation level or above, as the EdgeHub Connect SDK does.
    • in a container of a runtime this agent does not know (Linux): the agent tells apart the containers of Docker and Podman only. Run the application in a Docker or Podman container, or on the host.
    • outside this agent's pid namespace (Linux): the agent cannot see the application's process, as when the agent itself runs in a container. An administrator installs the agent on the host.
    • the container's application labels are longer than any application name (WSL 2): the relay found labels too long to name an application. Create the container again with the labels set to the application's type and name.

    Any other reason means the agent failed to identify the caller, and gets 503 Service Unavailable: asking again may succeed. In WSL 2, a container whose relay edgehub-agent.exe wsl setup installed from an earlier agent gets 403 Forbidden for these too, until wsl setup runs again.

    • the peer exited before it could be identified, the process at the peer's pid does not hold the connection, or pidfd_open: no such process: the process that connected to the agent exited, or handed its connection to another process and closed its own, while the agent was identifying it. The agent identifies the process that connects, so that process has to keep its connection, and stay alive, until it has the answer. If the application does this every time, change how it connects.
    • A reason that ends in operation not permitted or permission denied, every time: a restriction keeps the program that identifies callers from making the call the reason names, such as a system call filter that denies pidfd_send_signal or pidfd_open. On a Linux device, look at the agent's service, such as a SystemCallFilter= in its unit; for a container in WSL 2, look at the relay's service in that distribution, edgehub-wsl-relay.service, not at the agent on Windows.
    • Any other reason names the read or the system call that failed, in the agent or, for a container in WSL 2, in the relay in its distribution. If it returns, an administrator removes the cause it names.

    The agent's log has the same reason as the application.

  • applications are provisioned through the agent's local pipe or socket, never over the network

    The request came over the network. Applications ask from the device itself, through \\.\pipe\edgehub_app on Windows or /run/edgehub/app.sock on Linux, as the EdgeHub Connect SDK does.
