GET /edgehub/api/connection

Get connection status.

  • Request Headers

    Log in with the OS or the "admin" account to get a JWT token (token field from the response body).

    Authorization: Bearer <token>

  • Response 200 OK

    {
    "enabled": true | false,
    "status": "connected | disconnected",
    "certRevoked": true | false, // since 1.2.0
    "stormDetected": true | false, // since 1.3.1
    "configUnusable": true | false, // since 2.4.0
    "errorMsg": "<the detail error message>" // optional
}

    certRevoked: indicates whether the certificates are revoked or not

    stormDetected: indicates whether there is a connection storm

    configUnusable: indicates that a connection setting is stored but could not be loaded, so it was refused rather than erased. The device is still provisioned and the setting is still on disk; errorMsg carries the reason. Do not present such a device as unprovisioned, because provisioning it again overwrites the setting that was kept.

    errorMsg: the reason for the current failure, when there is one

  • Response 401 Unauthorized

    {
    "Code": 401,
    "Message": "<the detail error message>"
}

POST /edgehub/api/connection

Enable or Disable the device connection.

  • Request Headers

    Log in with the OS or the "admin" account to get a JWT token (token field from the response body).

    Authorization: Bearer <token>

  • Request Body

    conncfg is optional.

    If the op is "connect" and the conncfg has been provided, it will set the connection setting first, then enable the connection to the cloud; if the conncfg is not provided, it will enable the connection only.

    If the op is "disconnect", it will disable the cloud connection. conncfg will be ignored.

    {
    "op": "connect | disconnect",
    "conncfg": {
        "username": "<username>",
        "password": "<password>",
        "mqttHost": "<QFDN or IP>",
        "mqttPort": 1883,
        "enableTLS": true | false,
        "overWebSocket": true | false,
        "connectionString": "<Azure IoT Hub Connection String>", // optional
        "mac": "AABBCCDDEEFF", // optional,
        "uuid": "123e4567-e89b-12d3-a456-426614174000" // optional
    }
}

    or

    {
    "op": "connect | disconnect",
    "conncfg": {
        // (since edgehub-agent 1.1.0)
        "deviceTokenCredential": "<base64-encoded device credential JSON>",
        "skipCertVerify": true | false
    }
}

  • Response 200 OK

GET /edgehub/api/provisioning/config

Get the current auto-provisioning configuration. (since edgehub-agent 2.3.0)

The agent auto-provisions on first boot by exec'ing the edgehub-bootstrap-provider binary and running a two-phase NATS exchange (WISE2J) with the ASAN server. This endpoint exposes the operator-tunable knobs for that flow; non-tunable values (server URL, hardware model, retry cadence) are built into the agent.

  • Request Headers

    Log in with the OS or the "admin" account to get a JWT token (token field from the response body).

    Authorization: Bearer <token>

  • Response 200 OK

    {
    "provider": "",
    "providerTimeout": "10s",
    "retry": {
        "maxRetries": 20
    },
    "tls": {
        "skipVerify": false
    }
}
    • provider: Absolute path to the edgehub-bootstrap-provider binary. Empty string means "look up the binary on PATH".
    • providerTimeout: Timeout applied to the provider-binary exec (Go duration syntax, e.g. "10s", "30s").
    • retry.maxRetries: Maximum number of retry attempts per NATS command before giving up.
    • tls.skipVerify: Disable TLS server-certificate verification during provisioning. Dev/test only.

  • Response 401 Unauthorized

    {
    "Code": 401,
    "Message": "<the detail error message>"
}

PUT /edgehub/api/provisioning/config

Update the auto-provisioning configuration. (since edgehub-agent 2.3.0)

The submitted provider path is normalized server-side (whitespace and surrounding quotes are stripped) and validated: when non-empty it must be an absolute path to an existing regular file that is executable on the current OS. An empty provider is valid and falls back to PATH lookup.

  • Request Headers

    Authorization: Bearer <token>

  • Request Body

    Same shape as the GET response.

    {
    "provider": "C:\\Program Files\\Advantech\\EdgeHub\\edgehub-bootstrap-provider.exe",
    "providerTimeout": "10s",
    "retry": {
        "maxRetries": 20
    },
    "tls": {
        "skipVerify": false
    }
}

  • Response 200 OK

    Returns the normalized and persisted configuration (the response echoes the post-normalization provider value, not the raw input).

  • Response 400 Bad Request

    Malformed request body or invalid duration string.

    {
    "message": "<the detail error message>"
}

  • Response 401 Unauthorized

    {
    "Code": 401,
    "Message": "<the detail error message>"
}

  • Response 422 Unprocessable Entity

    Validation failed. Common causes: provider path is not absolute, points at a missing file, is not a regular file, or (on Unix) is not executable.

    {
    "message": "<the detail error message>"
}

POST /edgehub/api/applications/provision

Register an application with the cloud under this device's identity, and return the credential the cloud issued for it. (since edgehub-agent 2.4.0)

An application credential is an identity of its own, separate from the device's: it carries its own devId and uuid and isApp: true, and shares the device's mac. The agent obtains it on the device's behalf and does not keep a copy; what the caller does with it is the caller's responsibility.

Provisioning is create-or-get. If the name is already registered for this device and type, the existing credential is returned rather than an error, so an application can call this on every start with the same name and receive the same credential each time. It also means that two applications which pick the same name share one identity; the agent logs a warning whenever it returns an existing registration.

Applications running on the device normally obtain their credential through the EdgeHub Connect SDK rather than by calling this endpoint over HTTP.

  • Request Headers

    Log in with the OS or the "admin" account to get a JWT token (token field from the response body).

    Authorization: Bearer <token>

  • Request Body

    {
    "type": 3,
    "appName": "Line 3 Sensor",
    "timeoutMs": 60000,
    "x509": 1
}
    • type (required): The application type: 1 EdgeLink, 2 SCADA, 3 Application.
    • appName (required): The application name, following the rules below.
    • timeoutMs (optional): How long the agent may spend on the request, in milliseconds. Absent, zero or negative means the default, 60000; values above 300000 are capped there. A new registration usually takes a few seconds, so a value of a few seconds or less may expire before the cloud answers.
    • x509 (optional): Whether the credential includes client certificates: 1 yes, 0 no. Absent means 1, except for SCADA (type 2), which defaults to 0.

  • Application Name Rules

    A name is accepted when it

    • is 1 to 32 characters long,
    • is made of letters and digits in any script, combining marks, and the separators -, _ and space,
    • contains at least one letter or digit,
    • neither starts nor ends with a separator, and has no two separators in a row, and
    • writes every character in its standard form: full-width Latin such as Ｓｅｎｓｏｒ and half-width katakana such as ｾﾝｻｰ are refused, while Sensor and センサー are accepted.

    Emoji, punctuation such as . and /, and invisible characters are refused. Leading and trailing spaces are not trimmed; they are refused like any other separator at either end.

    Names are compared without regard to case: Sensor01 and sensor01 are one application. The same name can be registered once for each type. EdgeLink and SCADA are reserved for types 1 and 2, and cannot be used as the name of a type 3 application.

  • Response 200 OK

    {
    "credentialString": "{\"devId\":12345,\"name\":\"Line 3 Sensor\",\"isApp\":true,\"type\":\"Application\",\"uuid\":\"00000000-0000-0000-0000-000000000000\",\"mac\":\"001122AABBCC\", ...}"
}
    • credentialString: The credential exactly as the cloud issued it: a JSON document, encoded as a string. Parse it as JSON. The agent does not reshape it, so fields the cloud adds later pass through unchanged.

    When x509 is 0, the credential's x509 object holds only ca, revokeUrl and status. The certificate and key fields are absent, not empty.

  • Response 401 Unauthorized

    {
    "Code": 401,
    "Message": "<the detail error message>"
}

  • Response 422 Unprocessable Entity

    The request itself is wrong and will be refused again as it stands: a malformed body, an unknown type, an unacceptable appName, or an undefined x509 mode. Change the request before sending it again.

    {
    "message": "invalid application name: \"Sensor.01\" contains U+002E, which is not a letter, a digit, a combining mark, or one of the separators '-' '_' and space (CHAR:U+002E)"
}

    When the name breaks one of the rules above, the message ends with the rule's identifier in parentheses, which is stable and safe to match on: LENGTH:<n>, COMPAT:U+XXXX, CHAR:U+XXXX, NO_LETTER_OR_DIGIT or SEPARATOR_PLACEMENT. A reserved name is refused without one, as invalid application name: "EdgeLink" is reserved for another application type.

  • Response 502 Bad Gateway

    The cloud answered and refused, or answered in a form the agent could not read. The message carries the cloud's reason, for example APP_INVALID_X509. Sending the same request again will not change the answer.

  • Response 503 Service Unavailable

    The agent could not do the work, and nothing about the request was wrong: it is not connected to the cloud yet, which is normal for a short while after it starts; it is shutting down; or the cloud never answered. Retry. Retrying is safe: provisioning is create-or-get, so a later attempt returns whatever an earlier one registered.

  • Response 504 Gateway Timeout

    The request ran out of time before the cloud answered. The registration may or may not have been made; retrying with the same name is safe for the same reason.

POST /edgehub/api/initialcode

Retrieve the current initial code for device registration.

  • Request Headers

    To access this endpoint, log in with an OS or "admin" account to obtain a JWT token (token field in the response body). Include the token in the request header.

    Authorization: Bearer <token>

  • Response 200 OK

    {
    "code": "9c46e07d81d247614cfb053bca94c45080b52086d425728aa88ba338b1cdd453"
}
    • code: The current initial code for the device registration process, valid for a specific time period before regeneration.

Initial Code Retrieval

The initial code required for device registration can be retrieved by either of the following methods:

  1. mDNS Browsing:

    • The initial code is broadcasted over the local network via mDNS under the service name _edgehub._tcp.local..
    • To retrieve the initial code, clients can browse the mDNS service and filter the TXT record, where the code field appears as code=<initial code>.
    • This method is suitable for trusted internal networks where mDNS broadcasts are accessible, and it allows clients to dynamically discover the initial code without direct API access.

  2. REST API Request:

    • Alternatively, clients can retrieve the initial code using the POST /edgehub/api/initialcode endpoint, which requires authorization via a JWT token obtained through login.
    • This approach provides direct access to the latest initial code when mDNS may not be available or accessible.

These options allow clients flexibility in retrieving the initial code based on network availability and security requirements.

POST /edgehub/api/device/challenge

Initiate a device challenge by generating a key that authenticates the request.

  • Request Headers

    This request does not require JWT-based authorization, as it relies on a challenge-response authentication mechanism.

  • Request Body

    {
    "clientID": "<string>",  // Unique identifier generated by the client
    "key": "<string>"        // HMAC and bcrypt-derived hash
}
    • clientID: A unique identifier generated by the client. This value is combined with an initial code (server-generated and updated periodically) to create a key.
    • key: A hashed value used to verify the client. The key is generated by combining clientID and initial code using HMAC and bcrypt.

  • Key Generation Process

    To generate the key, the client combines its unique clientID and the server-provided initial code (which can be obtained via mDNS or by calling POST /edgehub/api/initialcode). Here's the process in detail:

    1. Concatenate clientID and initial code into a single string.
    2. Generate an HMAC using SHA-256, with the initial code as the secret key and the concatenated string as the data.
    3. Hash the HMAC result with SHA-256 to ensure no NULL bytes are included, producing a consistent output for bcrypt.
    4. Hash the SHA-256 result using bcrypt to produce a secure, one-way key value.
    5. Convert the bcrypt result to a hex string to get the final key.

    Note: This approach ensures the key is unique and valid only while the initial code is active, providing secure and time-limited access to device registration.

    Example in Golang:

    func GenerateKey(initialCode, clientID string) (string, error) {
  data := fmt.Sprintf("%s%s", clientID, initialCode)
  h := hmac.New(sha256.New, []byte(initialCode))
  h.Write([]byte(data))
  hmacResult := h.Sum(nil)

  // Hash the HMAC result with SHA-256 to ensure no NULL bytes are included.
  sha256Result := sha256.Sum256(hmacResult)

  // Generate bcrypt hash from SHA-256 result.
  bcryptHash, err := bcrypt.GenerateFromPassword(sha256Result[:], bcrypt.DefaultCost)

  if err != nil {
    return "", err
  }

  return hex.EncodeToString(bcryptHash), nil
}

  • Response 200 OK

    {
    "code": "<string>"  // A new code for the client to use in subsequent requests
}
    • code: A server-generated code for continued access, stored for clientID and used for /api/device/register requests.

  • Response 400 Bad Request

    {
    "message": "<the detail error message>"
}

    This error occurs if the clientID or key is not found or is invalid.

  • Response 401 Unauthorized

    {
    "message": "Unauthorized"
}

    This error occurs if the key validation fails.

POST /edgehub/api/device/register

Complete the device registration process with clientID, code, and additional registration details. The device will connect to the EdgeHub once the registration process is successful.

  • Request Headers

    No JWT-based authorization is required for this endpoint, as it uses the challenge-response mechanism for validation.

  • Request Body

    {
    "clientID": "UKmEjSdv6Apcz4fC",
    "code": "d38c58c86d1dc04a0723940cb767454c45da3f54877d92c5b91aec7420417657",
    "timestamp": 1730158176,

    "baseUrl": "https://api-dm-center-master-ensaas.edge365.advantech.com/v1.1",
    "orgId": 10,
    "token": "eyJhbGciOiJIUzUxMiIsInR5cCI6IkpXVCJ9..."
}
    • clientID: Unique identifier generated by the client.
    • code: Generated response code based on the challenge code and timestamp provided during the challenge-response process.
    • timestamp: The current client-side time when generating code.

    Additional Registration Fields:

    • baseUrl: The base URL for the device management API, selected from the station list.

      • https://bi.wise-deviceon.advantech.com/api/stationList
      • https://wise-deviceon-bi.azurewebsites.net/api/stationList

      • Within each station's data, the url_apidm field represents the possible baseUrl values. For example:

        {
    "stationList": [
        {
            "name": "EdgeSync360/EdgeHub Master Station",
            "url": "https://pivot-api-hub-master-ensaas.edge365.advantech.com",
            "url_apidm": "https://api-dm-center-master-ensaas.edge365.advantech.com/v1.1"
        }
    ]
}

    • orgId: Organization ID from the selected tenant's organization data. This value is retrieved from the tenant array in the {baseUrl}/connect/login response.

    • token: JWT access token obtained from the {baseUrl}/connect/login response. The accessToken field in the response body represents this token.

  • Code Generation Process

    The client generates code as follows:

    1. Concatenate clientID, challenge code, and timestamp into a single string.
    2. Generate an HMAC using SHA-256 with the initial code as the secret key and the concatenated string as data.
    3. Convert the HMAC result to a hex string to produce the final code.

    Example in Golang:

    func GenerateResponseCode(initialCode, clientID, challengeCode string, timestamp int64) string {
    data := fmt.Sprintf("%s%s%d", clientID, challengeCode, timestamp)
    h := hmac.New(sha256.New, []byte(initialCode))
    h.Write([]byte(data))
    return hex.EncodeToString(h.Sum(nil))
}

  • Response 200 OK

    {
    "message": "Device registered successfully",
}

  • Response 400 Bad Request

    {
    "message": "<detailed error message>"
}

    This error occurs if the baseUrl, orgId or the token is not found or is invalid.

  • Response 401 Unauthorized

    {
    "message": "<detailed error message>"
}

    This error occurs if the code validation fails.

  • Response 500 Internal Server Error

    {
    "message": "<detailed error message>"
}

    This error occurs if device registration or onboarding fails.
